# 사진 보내기와 사진·글귀 관리의 연결

2026-10-28 · 경로 비교와 최종 구현 기준 · 공통계약 v1.17

사용자는 자동 글귀 작성과 기능 중심 관리 화면 구현을 요청했다. 감정적인 로딩·책장 넘김·BGM·완성본 감상은 NFC에 남긴다. 기존 `/review`의 큰 사진/글귀 편집 화면을 새 관리 UI와 같은 것으로 보지 않는다. 아래 경로 비교와 모형은 설계 이력이며, 최종 정책은 실제 관리 UI/API와 글귀 worker에 연결했다. 승인된 격리18187 반영·검증 범위는 [개발운영](../../개발운영.md)의 최신 절을 따른다. 비교 모형 자체는 여전히 합성 데이터만 사용한다.

## 권하는 구성

**처음은 보내기, 재방문은 관리. 같은 앨범의 두 작업 화면으로 연결한다.**

| 진입 당시 상태 | 기본 화면 | 이유 |
|---|---|---|
| 사진이 없는 새 앨범 | 카카오톡식 사진 보내기 | 빈 관리 화면을 먼저 거치지 않음 |
| 탭에 미전송 사진/실패한 전송/전송 중 항목이 있음 | 기존 보내기 화면 이어가기 | 파일과 진행 상태를 숨기거나 전송을 취소하지 않음 |
| 저장 사진이 있고 미완료 전송 없음 | 사진·글귀 관리 | 이미 한 일을 반복하지 않고 내용을 바로 확인 |
| 관리 중 사진 추가 선택 | 보내기 화면 | 본래의 첨부/보내기 친숙함 보존 |
| 추가 전송 후 | ‘사진·글귀 확인’으로 관리에 복귀 | 완료 순간 강제 이동/입력 가로채기 없음 |

- 동일 앨범 ID/관리 권한/제목을 유지한다. 두 URL을 고객이 골라 들어가게 하거나 초기 탭 선택을 요구하지 않는다.
- 서버에 저장된 사진 여부는 서버 상태, 전송 이어가기는 해당 계정/앨범의 개인 탭 draft로 판정한다. 로컬 파일은 영속 저장하지 않으며 새로고침 이후 복원을 약속하지 않는다.
- 업로드 완료가 자동으로 다른 화면으로 이동시키지 않는다. 바이트 저장/글귀 처리 상태가 시점마다 다를 수 있으며 ‘사진·글귀 확인’은 해당 항목의 현재 상태를 보여준다.
- 관리 화면은 작은 순번/사진과 옆의 글귀를 순서대로 표시한다. 긴 글쓰기/완성본 연출/책 넘김/음악을 넣지 않는다.
- 글귀는 공통 편집 후 입력하며 800ms 또는 입력창 이탈 시 자동 저장한다. 각 사진별 저장 버튼·전체 저장·완료 확인을 중복 제공하지 않는다. 저장 실패 재시도·충돌 선택·이탈/로그아웃의 미저장 내용 보호를 제공한다.
- 사진별 추가/삭제/순서 변경은 필요한 곳에서만 제공한다. 정상 화면에 전송 준비/예약/검증/디코드 같은 내부 단계를 늘어놓지 않는다.

페이지 수와 단순성은 같은 수치가 아니다. 한 화면의 도구를 줄여 목적을 분명히 하는 것이 이번 선택 기준이다. 필요한 때 세부 도구를 드러내는 원칙은 [Apple Disclosure controls](https://developer.apple.com/design/human-interface-guidelines/disclosure-controls), 긴 편집을 중첩 모달 안에 넣지 않는 기준은 [Apple Modality](https://developer.apple.com/design/human-interface-guidelines/modality)를 참고한다. 이 가이드가 Mori의 선호/성과를 실증한 자료는 아니다.

## 네 가지 흐름 비교

`simulate.py`가 4안 × 26상황 = 104개의 결정론적 경로를 생성한다. 실제 사람/기기/네트워크를 104회 테스트한 것이 아니다. 아래 수치는 **업로드/관리 화면 사이 전환만** 세며 OS선택기, 사진 선택 탭, 편집, 전송 시간은 포함하지 않는다. 사용성 점수/성공률/선호 비율을 만들지 않는다.

| 안 | 첫 전송만 | 처음 전송→내용 확인 | 재방문→내용 확인 | 재방문→추가→내용 확인 |
|---|---:|---:|---:|---:|
| 항상 업로드부터 | 0 | 1 | 1 | 1 |
| 항상 관리부터 | 1 | 2 | 0 | 2 |
| 한 화면에 모두 | 0 | 0 | 0 | 0 |
| 상태에 따라 시작 | 0 | 1 | 0 | 2 |

한 화면 안은 화면 전환이 가장 적다. 사진 전송과 글귀 편집 도구가 동시에 보이는 부담은 아직 **설계 가설**이며 인지부하를 측정하지 않았다. 상태에 따른 시작안도 추가 업로드의 왕복은 2회로 항상 업로드부터인 안보다 많다. 첫 준비와 재방문 확인에서 불필요한 출발 단계를 없애고 작업 맥락을 분리한다는 기준으로 추천한다. 무조건 모든 사례의 최소 동작을 달성하는 안이라고 주장하지 않는다.

사례: 첫1/12/20장, 전송만 하고 종료, 선택 취소,21장초과,오프라인,1장실패,미전송사진보유중확인,미전송/전송중재방문,저장사진보기/글귀수정/순서수정/추가/2회추가/삭제/재시작,글귀대기/실패/미저장추가,마지막사진삭제,다른탭충돌,로그아웃,NFC준비중,완성후관리진입을 포함한다. 실패·충돌을 해결했다고 보는 테스트가 아니라 필요한 보호 조건을 경로에 명시한다.

## 실제 동작과 기술 경계

`ALBUM_CONTENT_ENABLED` 활성 상태에서 `/manage`는 기능 중심 관리를, `/edit`는 카카오톡식 전송을 담당한다. 기존 `/review`도 새 관리 화면으로 연결한다. 새 모드는 published에도 사진을 수정할 수 있고 빈 앨범은 전송으로 연결한다. 기존 generation의 가로 AI를 재사용하지 않고 `album_content` 전용 글귀 작업이 정규화 사진으로 최초 문장만 준비한다. 기존 run/snapshot/결과를 backfill하거나 고객 앨범을 일괄 재생성하지 않는다.

교체는 새 파일 검증 완료 전까지 원래 사진을 유지하며 같은 위치/글귀로 원자적으로 바꾼다. 자동 글귀가 늦게 도착해도 사용자가 쓴 글을 덮어쓰지 않는다. 현재 자료가 준비되면 감상 목록을 자동 공개하며, 추가 준비 중에는 직전 준비된 목록을 유지한다. 새 NFC 세션은 입장 당시 목록/사진을 고정해 진행 중 수정에 끊기지 않는다. 만료·태그 폐기·앨범 삭제의 접근 차단은 유지한다.

읽기 전용 TASK-007-02는 자동 완성과 첫 NFC 감상 후 수정기간 시작, 약7일 수정 허용을 기록하지만 기간/후속수정 운영은 검토안이다. 최신 사용자 결정인 자동 선별/AI3:4 제외,20장부터,관리와감상연출분리가 우선한다. 기간 정책은 아래 최신 사용자 확정과 구현을 따른다.

## 사용자 확정 — 2026-10-28 후속 답변

- 사진 저장과 자동 글귀 준비가 끝나면 NFC 감상을 자동으로 연다. 별도 ‘앨범 완성’ 버튼과20장필수조건은 두지 않는다.
- 첫 NFC 감상 전후 모두 기간 제한 없이 사진 추가·삭제·교체·순서 변경을 허용한다. 약7일잠금은 현재 적용하지 않고 반응을 본 뒤 재검토한다. 이는 정원20/내부50이나 AI 비용 한도를 없애는 결정이 아니다.
- 자르기·필터·보정은 포함하지 않는다. 기존 글귀 수정은 유지한다.
- 사진 교체 시 기존 글귀 유지·AI 추가 호출 없음으로 사용자 확정됐다. 새 파일 선택 취소/전송 실패 시 기존 사진이 남고 준비된 새 사진으로만 원래 위치에서 바뀐다.
- NFC 감상 자동 준비/완성 후 변경을 제품에 연결했다. 실기기 NFC 접촉·소리·손가락 드래그 인수는 별도다.

## 버튼을 줄이는 관리 화면 제안

평상시 공통 ‘＋ 사진’과 ‘편집’만 보이고 글귀는 읽기 상태다. 사용자 최종 지시에 따라 글귀 작성도 공통 편집 후에만 가능하다. 편집을 누른 동안에만 사진 삭제(−), 사진 위 ‘바꾸기’, 순서 손잡이를 드러낸다. 손잡이는 끌어서 옮기고, 탭/키보드 방향키로도 이동 가능하게 한다. ‘편집 마치기’는 도구를 접는 동작이며 감상 활성화/별도 저장 승인이 아니다. 사진마다 상시더보기 방식과 비교하는 합성 모형은 [/editing](http://192.168.0.120:18192/editing)이다. 버튼이 없는 길게 누르기 전용 안은 발견성과 조작 대안 부족 때문에 주경로로 추천하지 않는다. 이는 설계판단이며 사용자 선호 검증 결과가 아니다. 근거는 [Apple Context menus](https://developer.apple.com/design/human-interface-guidelines/context-menus), [Gestures](https://developer.apple.com/design/human-interface-guidelines/gestures)를 참고한다.

모형은 글귀 수정·편집도구 접기/펼치기·사진 확인·추가/교체 취소·합성교체·삭제 확인·손잡이/방향키/메뉴 이동을 비교한다. 이 모형 자체는 실제 전송·자동 글귀 API를 호출하지 않는다. 별도 제품 구현과 모형 모두 확정 정책대로 교체 시 기존 글귀를 보존한다. 실제 제품에서 현재 즉시삭제 API에 없는 실행취소 기능을 약속하지 않고 삭제 때 명시 확인을 유지한다.

## 조작 가능한 모형

같은 Wi-Fi/Mac/프로세스 실행 시 [브라우저 비교](http://192.168.0.120:18192/management). 상단에서 네 안/빈 앨범/기존 앨범/재방문을 비교한다. 제품에 이 선택기를 넣는다는 뜻이 아니다. 합성 사진/문장만 사용하며 실제 AI·저장·업로드 API가 없다. 수정 내용은 모형 메모리에만 남는다. 현재 모형은 전송 성공 경로와 선택·재방문·수정 보존을 조작하며,26개 예외를 모두 UI로 구현한 것이 아니다. `traces.json`/`summary.json`에 전체 모델 경로를 저장한다.
