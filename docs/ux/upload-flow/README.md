# 업로드 페이지 UX 재설계·비교 제안

2026-10-28 · 중간안 제품 구현 · 공통계약 v1.16 유지

추가 비교 요청: `three-upload-flows.html`은 **보내기 한 번 / 선택 즉시 전송 / 카카오톡식 묶음 전송** 세 안의 전용 비교다. 세 번째 ‘이전에 제시한 것’은 우선 사용자의 카카오톡식 전송 방향으로 해석해 재구성했으며 원본 카카오톡 UI를 복제하거나 실제 모바일 동작을 검증한 것은 아니다. 현재 서비스 화면을 뜻하는지에 대한 확인 질문은 별도로 제시했다. 공통 상황과 단계 바로가기로 같은12/20장·기존8장추가·초과21장·끊김·실패 조건을 불러올 수 있다. 단계 바로가기는 비교용 정지 화면이며, 각 안 처음부터 체험에서는 선택→전송→완료를 모의 재생한다. 원래432안 탐색과 단계별확인 후보는 `upload-comparison.html`에 보존한다.

기본 비교 지점은 사진 선택 직후다. 카카오톡식 안은 하단 첨부 영역→보내기→메시지 형태의 사진 묶음으로 구성했다. A안은 선택 사진 전체가 주 영역, 카카오톡식 안은 첨부 요약에서 선택적으로 전체 사진을 펼친다. 따라서 두 안의 필수 보내기 횟수는 같고 사진 확인·저장 묶음의 배치가 다르다. 모형에서 세 안의 선택 직후 보내기 유무, 카카오톡식12장 확인/전송완료, 기존8장+12장의두묶음, 실패11/12상태, 초과21장보존/해제후활성화, 프레임320/390가로overflow없음을 확인했다. 초기 모형에 빠진 scenarios선언을 수정한 뒤 해당 확인을 진행했다. 제품 코드·계약·DB 변경이나 실파일 전송은 없다.

대화 내 화면을 지원하지 않는 기기에는 **일반 브라우저용 비교 페이지**를 제공한다. 재실행은 저장소 루트에서 `python3 docs/ux/upload-flow/serve_browser_preview.py --bind <현재 LAN IP>`다. 2026-10-28 확인 주소는 `http://192.168.0.120:18192/`. 같은 Wi-Fi·Mac/프로세스 실행이 필요하며 IP 변경 시 재실행한다. 상단의 보내기 있음/바로 전송/카카오톡식 버튼으로 바꾸며 기존 단계/상황 선택을 유지한다. iframe·대화 표시 기능·외부 CDN 의존성 없이 해당 모형만 제공하고 실제 서비스/API/파일 업로드와 연결하지 않는다. 현재 공개 인터넷 배포는 없다. Mac Chrome에서 세 안 전환·최종 상태·viewport320/390 가로overflow없음·콘솔오류없음을 확인했으며 실제 iPhone 접속 인수는 별도다.

## 최신 방향 — 안내 말풍선을 남긴 중간안

사용자는 최소 문구안이 허전하고, 이전 카카오톡식의 안내 말풍선이 익숙함을 만든다고 구체화했다. 따라서 `http://192.168.0.120:18192/balanced`의 **중간안 / 이전 카톡식 / 최소 문구안**으로 비교한다. 안내 한 문장과 말풍선 형태는 남기고 반복 제목/설명/장수는 줄였다. 사용자가 “중간안이 좋은 것 같아. 적용해줘.”로 채택했다. 안내는 비교 기본값인 첫 전송 전까지만 표시하고, 제품의 EasyAlbumUpload에 반영했다. API/DB와 v1.16 계약 버전은 유지한다. 아래 최초 제안·비교의 미적용 설명은 당시 이력이다. 검증·실행 상태는 개발운영 최신 절을 따른다.

## 직전 방향 — 카카오톡식 간결화

후속 사용자 반응으로 아래 최초 추천의 ‘한 화면·보내기 한 번’은 후보에서 제외한다. 바로 전송과 카카오톡식 비교는 유지하며, 카카오톡식의 친숙함·낮은 거부감을 보존하고 필요한 텍스트만 남긴다. [해석·근거·간결화 제안](refined-direction.md), 새 비교 주소 `http://192.168.0.120:18192/refined`를 따른다. 새 추천은 간결한 카카오톡식이며 사용자 전체 선호의 우위나 최종 채택·제품 적용은 아직이다. 최초432안의 기록과 데이터는 설계 탐색 이력으로 보존한다.

## 최초 추천 기록

**한 화면에서 사진을 고르고, 보내기를 한 번 누른 뒤, 같은 자리에서 저장을 확인한다.**

사이트에서 정상 경로의 필수 동작은 `사진 고르기`와 `N장 보내기` 두 번이다. 휴대폰 선택기 안의 사진 선택과 `추가/완료`는 별도이며, 전체 과정을 총 두 탭이라고 부르지 않는다. 사진 고르기 자체의 고민까지 사라진다고 주장하지 않는다.

별도 시작 안내, 앨범 선택/연결, 화질·형식·업로드 방식 선택, 제목 작성, 사진별 승인, 최종 확인 팝업, 저장 후 완료 버튼을 두지 않는다. 사용자가 보는 핵심은 **어떤 사진인가 / 보냈는가 / 저장됐는가** 세 가지다.

## 탐색 당시 화면과의 차이

현재 `EasyAlbumUpload`도 사진 선택과 보내기를 지원한다. 큰 화면 제목·빈 앨범 카드·사진 관리 목록·모든 파일 상태 문구·보내기와 사진 고르기 버튼이 한꺼번에 노출돼 관리 화면의 인상이 남는다. 전송 엔진 개선과 UX 재설계는 구분한다.

| 요소 | 현재 | 추천안 |
|---|---|---|
| 첫 화면 | 큰 소개 제목, 빈 카드, 장수, 사진 고르기, 상시 안내 | 앨범 맥락, 한 문장, 사진 고르기 하나 |
| 선택 후 | 관리 사진과 대기 사진·상태가 같은 격자에 섞임 | 이번에 보낼 사진을 주 영역으로, 기존 사진은 보조 영역 |
| 하단 | 보내기와 사진 고르기가 함께 큰 버튼 | 보내기가 주 행동, 추가 선택은 작은 보조 동작 |
| 사진 위 표시 | 모든 사진에 준비/대기/전송/확인 등의 문구 | 정상 상태는 하단 한 줄로, 사진에는 저장 체크·최종 실패만 |
| 완료 | 관리 틀과 상시 업로드 안내 유지 | 사진의 자리 유지, 저장 완료와 떠나도 되는 시점 표시 |
| 끝나는 조건 | 기능적으로 저장, 체감상 다음 단계가 모호 | 저장만으로 이번 작업 종료. 확인/앨범 완성 강요 없음 |

## 탐색 방법과 한계

색상만 바꾸는 대신 동작과 정보 구성이 달라지는 여섯 축을 조합했다.

| 축 | 비교한 구성 |
|---|---|
| 진입 6종 | 바로 사진 추가 / 소개 후 시작 / 단계 안내 / 대화 안내 / 자동 선택기 열기 / 가져올 곳 선택 |
| 선택 사진 3종 | 격자 / 가로 띠 / 파일 목록 |
| 전송 시작 3종 | 선택 즉시 전송 / 보내기 한 번 / 별도 검토 후 전송 |
| 진행 2종 | 같은 화면 / 전송 전용 화면 |
| 완료 2종 | 사진 목록 유지 / 별도 완료 화면 |
| 복구 2종 | 남은 파일만 / 묶음 전체 다시 선택 |

`6×3×3×2×2×2=432`개 구조 조합을 생성했다. 각 조합에 진입·선택·전송·저장·일부 실패·초과 선택의 여섯 화면 명세를 붙였다. 이는 **2,592개의 화면 상태 명세이며, 손으로 그린 2,592개 시안이나 실기기 스크린샷이 아니다.** 비교 화면의 구조 조합 탐색기에서 각 조합을 조작할 수 있다. 사용 가능한 마지막 9개는 상세한 설계 판단으로 비교했고, 핵심 3개를 별도 모형으로 제시한다.

각 조합에 12개 작업을 대입한 결정적 walkthrough는 5,184개다. 작성한 규칙을 실행하는 모델이며 실제 사용자 5,184명의 행동, 성공률, 선호나 시간 계측이 아니다. 유리한 점수를 임의로 합산해 우승안을 만들지 않았다. 모델이 세는 것은 사이트 행동·화면 상태·재선택 요구·전송 전 확인 기회다. 인지 부담·신뢰·심미성은 설계자의 가설로 남긴다.

12개 상황: 1장 / 12장 / 20장 정상, 선택기 취소, 잘못 고른 사진, 추가 선택, 21장 초과, 네트워크 중단·복귀, 1장 실패, 기존 8장에 추가, 보내기 중복, 브라우저 종료·재진입.

### 후보를 줄인 판단

| 기준 | 남은 조합 | 판단 이유 |
|---|---:|---|
| 전체 | 432 | 구조 탐색 범위 |
| 직접 사진 추가 | 72 | 이 페이지에 이미 업로드하러 왔으므로 시작 안내/출처 질문을 줄임. 자동 선택기 열기는 맥락과 사용자 동작 제한도 확인 필요 |
| 파일별 복구 | 36 | 실패 때문에 저장된 사진까지 재선택시키지 않음 |
| 같은 화면에서 진행 | 18 | 사진이 사라져 다른 단계로 이동하는 느낌을 줄임 |
| 완료 후 같은 목록 | 9 | 별도 완료 확인을 필수로 만들지 않음 |

이 필터는 본 과제의 단순함·맥락 유지 기준에 따른 **선택**이다. 일반적으로 모든 모달·완료 화면이 나쁘다는 실험 결과가 아니다. 권한이 없거나 로그인/선물 등록이 필요한 경우 기존 권한 경계를 우회하지 않는다. 모델은 업로드 권한이 있는 페이지에 도착한 이후부터 시작한다.

마지막 9개는 격자/띠/목록 × 즉시/한 번/별도 검토다. 격자는 사진 내용을 한 번에 확인하기 유리한 후보, 목록은 파일명·기술정보에 주의를 돌리는 후보, 가로 띠는 숨은 사진을 확인하려면 추가 탐색이 필요한 후보다. 격자 9칸/띠 3칸/목록 4행 가정은 모델의 화면 예산이며 기기에서 측정한 값이 아니다.

## 핵심 세 안 비교

| 안 | 정상 경로의 사이트 필수 행동 | 전송 전 확인 | 장점 | 부담/위험 |
|---|---:|---|---|---|
| 한 화면·보내기 한 번 `U009` | 2 | 있음 | 전송 의도와 선택 실수를 한 번에 확인. 화면 이동 없이 사진 유지 | OS 선택기 확인 뒤 사이트 보내기를 한 번 더 눌러야 함 |
| 선택 즉시 전송 `U001` | 1 | 없음 | 가장 적은 사이트 조작. 버튼에 ‘고르고 바로 보내기’ 명시 가능 | 잘못 고른 사진이 바로 전송됨. 전송 후 삭제·취소의 신뢰/정책을 먼저 검증해야 함 |
| 별도 검토 후 전송 `U017` | 3 | 있음 | 설명과 검토 영역 확보 | 사진 선택→다음→보내기로 같은 결정을 반복할 가능성 |

현재는 **U009**를 추천한다. 사진을 서버로 보내는 경계에서 명확한 동작 하나를 남기면서도, 추가 확인창과 완료 버튼은 없앨 수 있기 때문이다. 즉시 전송은 열등한 안으로 단정하지 않는다. 이후 실제 비교에서 사용자가 OS 선택기의 `추가`를 전송 동의로 자연스럽게 이해하고 오전송 복구도 충분하다면 더 적합할 수 있다.

현행의 ‘선택→보내기’를 그대로 채택한 뒤 점수로 정당화한 것은 아니다. 자동 전송이 행동 수에서 앞선다는 결과를 그대로 기록하고, 전송 통제라는 별도 판단 때문에 한 번 보내기를 추천한다. 이 한 동작의 가치가 없다면 제거하는 것이 맞다.

## 화면별 상세 설계 — 추천안

### 진입: 지금 해야 할 일을 하나만

- 작은 Mori 표시와 현재 굿즈의 앨범 이름. 앨범이 이미 연결돼 있으며 앨범 선택은 없다.
- 제목 `사진을 담아주세요`, 설명 `좋아하는 순간을 한 번에 골라주세요.`
- 핵심 행동 `사진 고르기` 하나를 엄지로 누르기 쉬운 하단에 배치한다.
- `최대 20장`은 정원 안내이며 20장을 채우라는 과제/진행률로 표현하지 않는다.
- 화질은 자동. 형식/해상도/MB·단계별 원리는 정상 화면에서 묻지 않는다.
- 빈 칸 여러 개를 로딩 skeleton처럼 보이게 그리지 않는다. 상시 돌아가는 로더도 없다.
- 기존 사진이 있으면 저장 사진과 수를 보여주되, 이번에 고를 사진이 우선이다. 추가 업로드가 없으면 이미 저장된 상태로 끝낼 수 있다.

### 휴대폰 사진 선택: 익숙한 선택기 그대로

- 사진 버튼을 눌렀을 때 OS 다중 선택기를 연다. 진입만으로 자동 실행하지 않는다.
- 카카오톡 전용 갤러리 UI를 모사해 브라우저가 제어할 수 없는 날짜/드래그 기능을 약속하지 않는다.
- 사진을 선택한 뒤 OS `추가/완료`로 돌아온다. 이 단계는 아직 서버 전송 동의가 아니다.
- 취소하면 그대로 이전 화면으로 돌아온다. 이미 고른 사진/저장 사진을 버리지 않는다.
- 시뮬레이터의 `예시 전체 선택`은 비교용 조작 도구이며 실제 서비스나 iOS 선택기에 새 버튼을 추가한다는 뜻이 아니다.

### 선택 후: 사진을 보고 한 번 보내기

- 같은 페이지의 제목이 `12장 선택했어요`로 바뀐다. 방금 고른 사진을 주 영역의 3열 격자로 보여준다.
- 파일명·크기·형식·각각의 ‘선택됨’ 문구는 숨긴다. 사진 비율은 미리보기에서만 정돈하며 저장 사진을 크롭하지 않는다.
- 사진 선택 해제는 각 사진의 작은 ×. **조작 영역은 최소 약44px**로 확보한다. 사진 자체를 누르면 개별 확인은 선택적으로 가능하게 설계한다.
- `더 고르기`는 보조 동작이며, 기존 선택에 추가한다. 새 선택기 취소/닫기 때문에 기존 선택이 없어지지 않는다.
- 하단 주 행동은 `12장 보내기` 하나. 누른 뒤 ‘정말 보내시겠어요?’를 다시 묻지 않는다.
- 미리보기 일부가 늦어도 준비되는 사진부터 표시한다. 모든 사진의 썸네일 생성이 끝나야만 보내기를 누를 수 있게 만들지 않는다.
- 전송 전에만 `전송이 끝날 때까지 화면을 열어주세요`를 보여준다. 첫 화면부터 긴 경고를 읽게 하지 않는다.

### 전송 중: 사진은 그 자리에, 상태는 한 줄

- 사진 위치를 바꾸거나 완료 순으로 재정렬하지 않는다. 정상 경로에서는 선택 해제·추가 버튼을 잠시 숨겨 전송과 관리가 경쟁하지 않게 한다.
- 하단 버튼 자리는 `8 / 12장 저장`과 실제 저장 개수 기반 진행 표시로 바뀐다.
- 전송 준비 중 처음에는 `사진을 준비하고 있어요`. 실제 파일 저장이 확인되면 해당 사진에 체크를 붙인다.
- 브라우저 전송 완료/검증 대기와 서버 저장 확정을 섞지 않는다. 모든 전송 바이트가 나갔어도 서버 확인 전에는 완료라고 하지 않는다.
- 매 파일의 준비→대기→전송→확인을 모두 글자로 나열하지 않는다. 오래 걸리거나 사용자 개입이 필요한 항목만 구체화한다.
- 가짜 퍼센트·미측정 남은 시간·연출용 지연을 넣지 않는다. 비교 모형의 타이머는 모의 동작이며 실제 속도 측정값이 아니다.
- 실수로 이탈할 때만 중단 가능성과 저장된 자료 보존을 설명한다. 정상 흐름에 필수 중단/계속 질문을 넣지 않는다.

### 저장 완료: 확인을 더 요구하지 않기

- 서버에서 이번 사진 모두의 저장이 확인되면 `12장 저장했어요` / `이제 화면을 닫아도 괜찮아요.`
- 격자와 순서는 그대로. 진행 표시만 사라지고 사진에 저장 표시가 남는다.
- `확인`, `완료`, `저장하기`를 추가로 누르지 않는다. 성공을 알리는 전면 모달이나 자동 화면 이동도 없다.
- 정원 미만이면 작은 `사진 더 담기`만 선택적으로 제공한다. ‘남은 8장 채우기’로 완성을 압박하지 않는다.
- 20장이 다 저장되면 추가 버튼은 숨긴다. 선택권 없는 비활성 버튼을 계속 보여주지 않는다.
- 이번 작업은 사진 저장까지다. `앨범 완성`, `NFC로 바로 감상`은 구현되지 않은 자동 publish/후속 제작을 약속하므로 표시하지 않는다.

## 예외에서도 흐름 유지

| 상황 | 사용자가 보는 것 | 서비스/후속 구현 조건 |
|---|---|---|
| 일시 연결 끊김 | `연결을 기다리고 있어요. 연결되면 남은 사진을 이어서 보내요.` | 현재 탭에서 파일을 보유한 경우에만 온라인 복귀 자동 재개. 완료 항목 유지 |
| 1장 최종 실패 | `11장 저장 · 1장 확인 필요`와 해당 사진 표시 | 다른 11장은 완료. 자동 복구를 먼저 하고, 소진 시 `남은 1장 다시 시도` 하나. 복구 불가능한 형식은 재시도로 해결된다고 약속하지 않음 |
| 오래 걸리는 1장 | 해당 사진 준비/확인 중, 완료 수 유지 | 실제 상태를 보이며 성공으로 숨기지 않음. 타임아웃 시 파일별 처리 |
| 21장 선택 | 21장 모두 유지. `20장까지 담을 수 있어요. 1장만 빼주세요.` | 앞 20장 자동 선택/전체 초기화 금지. 해제 즉시 보내기 가능 |
| 기존 8장 + 13장 선택 | 기존 저장 8장과 이번 선택 구분. 초과 1장 안내 | 합계 정원 검사. 새 선택만 쉽게 줄일 수 있게 함 |
| 선택기에 다시 갔다 취소 | 이전 선택 그대로 | 선택 취소가 대기 목록 삭제가 되지 않음 |
| 두 번 보내기 | 같은 진행 화면 | 요청 멱등성/접수 잠금 유지. 시뮬레이션만으로 DB 중복 방지를 검증한 것으로 보고하지 않음 |
| 브라우저 강제 종료/재시작 | 서버에 저장된 사진부터 표시. 미전송 사진은 재선택 필요 안내 | 현재 탭 메모리만으로 미전송 파일 복원 불가. ‘모두 복원’/백그라운드 무중단을 약속하지 않음 |
| 로그인 만료/권한 오류 | 사진을 공개하지 않고 필요한 로그인/권한 안내 | UX 단순화를 이유로 구매자/선물 등록/QR/NFC 경계 변경 금지 |

일시 실패의 자동 재시도와 영구 오류의 명시적 처리를 구분한다. ‘다시 시도’ 버튼 한 번을 모든 문제의 해법으로 쓰지 않는다. 대기 목록에서 빼기와 이미 저장된 사진의 삭제는 다르다. 저장 사진 삭제의 기존 확인 정책은 정상 전송 경로 밖에서 유지한다.

## 수백 장·동영상과의 관계

지금 비교의 제품 조건은 사진20장 저장이다. 500장 중20/50장을 자동 선별하는 기능은 제외됐으므로, 500장을 받아놓고 알아서 앨범에 들어간다고 안내하지 않는다. 단순히 이번 화면에 500장을 넣어도 안정성이 생기지 않는다.

향후 대량 입력도 선택/전송이라는 표면 흐름은 유지할 수 있다. 하지만 입력 자료함과 최종20/50장 정원을 분리할지, 선별·임시 보관·제외 자료 처리·영상 최적화/이어 올리기는 별도로 결정해야 한다. 무선 전환·메모리·발열·파일 지속성·브라우저 종료 검증이 필요하다. 이 제안은 그 기능 구현이나 승인 요청으로 확대하지 않는다.

## 실제 비교에서 볼 것

우선 아이폰15Pro에서 추천안과 즉시전송안 두 개를 비교한다. 같은 사진 묶음으로 하되 순서를 바꿔 학습 영향을 살핀다. 초기 5명 내외 관찰은 문제 발견용이며 우열의 통계적 증명이 아니다.

1. 설명 없이 첫 행동을 찾는지, 사진 선택 후 멈추는지 본다.
2. 일부러 잘못 고른 사진을 보내기 전에/후에 어떻게 고치는지 본다.
3. `언제 화면을 닫아도 되나요?`에 화면만 보고 답할 수 있는지 본다.
4. 12장/20장, 추가 업로드, 취소, 통신 끊김·복귀, 1장 실패를 확인한다.
5. 사이트 탭 수와 OS 선택기 탭 수, 선택 시작→첫 전송→마지막 서버 저장 확인 시간, 도움 요청, 재선택, 누락/중복을 따로 기록한다.
6. 사진 화질·HEIC/색·발열/메모리·화면 잠금은 별도의 실제 업로드 인수로 진행한다. 화면 모형 성공을 전송 성능으로 쓰지 않는다.

즉시전송에서 오전송이 늘지 않고 사용자가 더 자연스럽게 이해하면 추천을 바꿀 수 있다. 한 번 보내기에서 확인 기회가 유용하고 머뭇거림이 없으면 유지한다. ‘카톡과 비슷해 보이는가’보다 ‘설명 없이 원하는 사진을 저장했는가’를 우선한다.

## 근거와 산출물

- 읽기 전용 TASK-008의 카카오톡 미디어 전송 벤치마크·기기별 업로드 조사, TASK-007 통합 경험 기획안(2026-10-23)을 대조했다. 출처 경로와 확정 정책은 [재사용조사](../../재사용조사.md#간편-업로드-기획-대조--2026-10-27)를 따른다. 소스·환경·개인 사진을 복사하지 않았다.
- [NN/G 확인 대화상자 지침](https://www.nngroup.com/articles/confirmation-dialog/): 확인창은 오류를 줄일 때 유용하지만 반복되면 흐름을 방해한다. 별도 팝업 없는 보내기 동작은 이 과제의 설계 판단이다.
- [DWP 업로드 체크리스트](https://design-system.dwp.gov.uk/contribute/file-upload/summary): 업로드 규칙·여러 파일·사용자 피드백을 고려한다. Mori UI의 효과를 입증하는 비교 실험은 아니다.
- [W3C 상태 메시지](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html): 초점 이동 없이 저장·대기·오류 변화를 보조기술로 알 수 있게 한다. 실제 구현 시 집계 상태는 `role=status`, 개입이 필요한 오류는 적절한 오류 안내로 구분한다.
- [HTML 파일 입력](https://html.spec.whatwg.org/multipage/input.html#file-upload-state-(type=file)): OS 선택기 경계. [페이지 수명](https://developer.chrome.com/docs/web-platform/page-lifecycle-api): 페이지 중단/폐기 가능성.
