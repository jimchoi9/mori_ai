## 전체 환경 측정 방법

동일 fixture와 새 임시DB로 baseline 이미지2/글귀4와 새 이미지4/글귀4를 순서대로 실행한다. 현재 제품의 SDK request multipart/base64·JSON response decoding을 MockTransport로 통과시킨다. 외부 provider TCP/실제응답속도는 측정하지 않는다. 실제앱 HTTP/DB/codec·worker를 구동하며 프록시는 검증용 Python forwarding 대체물이다.

DB256+web384+proxy128+worker1024+driver128=1920MiB hard limit/no-swap로 서비스전체를2GiB예산 안에 고정분할한다. worker는1GiB, 기존codec child512MiB guard를 유지한다. 전체CPU quota합2.0이다. 하나의 공유2GiB부모cgroup과는 다르며 OS/Docker/VM은 합계 밖이다. 개별서비스 먼저 한도에 닿을 수 있다.

한 계측 라운드의 memory.current 합계 peak와 서비스별 memory.peak의 합(보수적인 상한)을 분리한다. cgroup사용량에는 page cache/커널이 포함되며 process RSS와 다르다. process RSS 합계도 별도 수집한다. 이 합계는 공유 페이지를 중복 계산할 수 있으므로 고유 물리 메모리 사용량으로 해석하지 않는다. idle anonymous memory 역시 RSS로 표현하지 않는다. 계측용dockerexec 자체 비용도 보수적으로 포함된다. 라운드 내 서비스 계측 시각 차이는 최대2 조건5.46초/4 조건3.49초여서 sampled 합계를 엄밀한 동시 peak로 부르지 않는다. 서비스별 peak 합은 이 한계를 보완하는 보수적 상한이다.

각 조건에서 12장 앨범+굿즈 생성을 4회 실행한다. 첫 회는 warmup, 이후 3회의 idle RSS를 warmup 직후와 비교한다. 조건별 앨범 생성48장(가로36·세로12, 쌍 업로드24·단일 업로드24), 추가12MP 앨범 검증4장, 굿즈12MP 업로드8회·생성4회다. AI 슬롯이 찬 뒤 추가 업로드를 요청하며 실제 codec 동시 구간 여부는 로그 근거와 구분한다.

제안판정은 worker≤819.2MiB, 전체≤1638.4MiB, OOM/limit·중복·미완료0, 실제 image2/4 도달과goods공존, warmup후idle기준 대비안정성이다. short최소검사는50장/30분 전체Task7와 운영OS전체메모리 수용 인증을 대체하지 않는다.

## 측정 결과와 판단

**판정: 이미지 병렬4의 운영 권고를 보류한다.** 최고 메모리는 제안 여유 기준 안에 들었지만, 병렬4의 warmup 후 유휴 RSS 증가가10% 기준을 넘었다. 이 결과만으로 RAM 증설이 반드시 필요하다거나 메모리 누수라고 단정하지 않는다. 제품의 이미지4·글귀4 코드는 변경하지 않았고, 운영 설정 변경이나 배포도 하지 않았다.

실행: `MORI_VERIFY_TEST_IMAGE=mori-ai:ai-tests bash scripts/verify-media-environment.sh`. Docker Linux/amd64 이미지가 Apple Silicon/arm64 Docker에서 실행된 에뮬레이션 환경이다. 각 조건은 새 DB·컨테이너에서 순차 실행했고 fixture SHA256이 일치했다. 프로그램은 두 조건의 엄격 인수 실패를 반영해 exit1로 종료했다. 기능 workload 성공과 메모리 인수 성공을 구분한다.

전체 idle RSS(MiB)는2 조건에서1098.30→1161.53→1181.67→1190.27,4 조건에서1076.56→1182.14→1220.29→1272.62였다. worker 자체 증가도 관측되어 driver만의 영향으로 돌릴 수 없다. Python allocator/캐시의 정상 유지인지, 추가 반복에도 증가하는 참조 보존인지 이번 짧은 시험으로 구분하지 못했다. 다음 판단에 필요한 작업은 동일4 조건에서 worker의 반복 후 잔류 메모리를 분해해 안정화 여부를 확인하는 것이다. 검증 driver의128MiB 압박도 별도로 해결해야 하며 기존 실패 기록을 삭제하거나 기준을 완화하지 않는다.

양쪽의 memory.max는 제품 서비스가 아닌 부하 driver에서 발생했다. driver의 anonymous memory가 주를 차지하므로 단순 파일 캐시라고 단정하지 않는다. 실제 운영 클라이언트와 다른 시험 구성의 제한이지만, 정해 둔 전체 no-pressure 체크는 양쪽 모두 실패로 남긴다.

원본 산출물: `output/task7-environment/jgsyd9rp/`의 manifest/host/summary와 조건별 samples·driver·provider·inspect·logs. 코드 SHA256·컨테이너 이미지 ID, fixture SHA256을 보존했다. 예비 실행의 DB 준비/계측 프로세스 경합 수정은 검증 도구 준비 실패이며 제품 OOM으로 집계하지 않는다.

측정의 추가 제한: production worker 진입 함수를 검증 모듈에서 직접 호출해 CLI logging 초기화는 실행되지 않았다. 따라서 worker span 로그가 없으며 추가 raw 업로드의 codec 실행 구간과 AI inflight의 정확한 중첩은 이 로그로 증명하지 못한다. 굿즈·앨범 AI 동시 실행은 provider 계측으로 별도 확인한다. storage read/write/copy·encode/decode 횟수와 API p50/p95, CPU 사용량/throttling은 이번 최소 측정에서 수집하지 않았다. 과거 버전 예약·run 복구 matrix도 이번 부하에 포함하지 않았으며 직전 셋째 묶음 회귀 결과와 구분한다.

독립 원시 결과 검토에서도 수치·판정이 일치했다. `provider.json`의 `peaks.goods/album`은 갱신하지 않는 필드여서0을 실제 관측값으로 사용하지 않는다. `provider-events.jsonl`에서 굿즈1·앨범2/4 및 공존을 확인했다. 전체 image peak와 호출 수 검사는 정상 동작했다.
