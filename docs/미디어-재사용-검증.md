# 재인코딩 없는 WebP 검증 — Task 1 판정

날짜: 2026-10-19. 범위: `docs/superpowers/plans/2026-10-19-webp-reuse-landscape-ai.md` Task 1의 안전성 탐색. 제품 코드·환경·DB·배포 변경 없음. Task 2 이후는 실행하지 않았다.

## 수정 결론 — 제품 요구에 맞춘 재판정

**클라이언트 WebP의 재인코딩 없는 재사용은 조건부로 가능하다고 판단한다.** 최초 보고의 ‘내부 payload 잔존 → 안전성 gate 불통과 → 허용 목록 없음’은 철회한다. 재사용 검사기가 구현·검증됐다는 뜻은 아니며, 현재 정상화 코드는 변경하지 않았다.

| 분류 | 근거와 의미 |
|---|---|
| 실행 가능한 공격 | 기존 시험은 코드 실행·XSS·서버 침해를 입증하지 않았다. 무해성 전체를 증명한 것도 아니다. |
| 실제 개인정보 유출 | 입증하지 않았다. 넣은 문자열은 합성 marker다. |
| 내부 바이트 보존 | VP8/VP8L/ALPH가 무시하는 추가 bytes의 보존은 실증됐다. 파일 수신자가 그 bytes도 받을 수 있다는 의미다. |
| 명시적 메타데이터 제거 | EXIF/GPS/XMP 등 식별 가능한 메타데이터를 파생본에서 제거하는 목적은 유지한다. |
| 모든 숨은 데이터 제거 | 제품의 승인 기준으로 추가하지 않는다. 내부 payload 잔존 자체는 재사용 불가 사유가 아니다. |

재사용 후보는 서버가 해시·형식·단일 프레임·크기·픽셀·방향·색상·소유권을 검사하고, EXIF/GPS/XMP 정리가 끝난 sRGB WebP다. 개인정보 메타데이터 청크 제거 등 컨테이너 정리만 필요하면 픽셀을 재압축하지 않고 처리할 수 있다. 확인된 sRGB ICC도 재사용 후보에서 일괄 제외하지 않는다. 방향 보정·색상 변환·축소가 필요한 파일만 필요한 픽셀 가공을 한다.

## 2. 실제 브라우저 생성 파일 검사

2026-10-19 Chromium **147.0.7727.15**에서 저장소의 현재 `frontend/src/features/uploads/preprocess.ts`를 TypeScript 타입만 제거해 그대로 실행했다. 외부 서비스/사용자 프로필 없이 독립 headless 브라우저와 합성 사진만 사용했다. 입력 768×1024에 EXIF 방향6·촬영일·GPS IFD·설명 marker를 넣었다. 실제 JPEG/PNG 입력의 메타데이터와 출력 RIFF 청크/EXIF/marker를 검사했다.

| 입력 | 현재 전처리 결과 | 출력 관측 |
|---|---|---|
| JPEG + EXIF/GPS/설명 | WebP 537,930 bytes, 1024×768 | EXIF/GPS/XMP 없음, 개인정보 marker 없음 |
| PNG + EXIF/GPS/설명 | WebP 537,864 bytes, 1024×768 | 위와 동일 |
| 일반 PNG | WebP 537,716 bytes, 768×1024 | 위와 동일 |
| PNG text | 원래 File 유지 | 댓글 marker가 남지만 서버 처리 입력이며 검증 완료 파생본 아님 |
| JPEG ICC | 원래 File 유지 | 현재 프론트의 보수적 색상 fallback |
| JPEG XMP | 원래 File 유지 | XMP/EXIF marker 보존, 기존 서버 정규화 필요 |

촬영일 `2026:10:19 12:34:56`은 WebP EXIF가 아니라 preprocessing 힌트로 따로 유지됐다. GPS/설명은 해당 힌트에 없다. 현재 코드는 4096/품질90이며 새 2048/85 설정의 검증으로 표현하지 않는다.

**브라우저 생성 ICC를 별도로 발견했다.** 변환된 본문 3개와 Canvas 썸네일 3개에 `VP8X / ICCP / VP8 ` 청크가 있었다. 본문 ICC는 모두 456 bytes, 이름/설명 sRGB, SHA256 `12afb4d9953adee0607d347daee5b78b18d6b3cab2d572b88970703f5edb37bc`로 동일했다. GPS/설명 등 원본 개인정보의 보존과 다른 현상이다.

한 본문 샘플에서 ICC→표준 sRGB 변환의 RGB 오차는 0이었다. ICCP 제거와 VP8X ICC flag 정리 후 압축 픽셀 재인코딩 없이 디코딩 픽셀도 동일했다. 이 프로파일은 무재인코딩 정리 후보이나 **프로파일 이름만으로 임의 업로드를 신뢰하지 않는다**. 알려진 bytes/실제 색상 특성을 검사해야 하며 모든 ICC 제거를 일반화하지 않는다.

썸네일은 현재 제품에 구현돼 있지 않다. 위 썸네일3개는 변환된 본문을 Canvas로 축소해 WebP를 만든 **별도 API 관측**이다. 본문과 같은 원본 bitmap에서 직접 만드는 향후 제품 흐름·정상 일치율·손실 누적 검증은 아니다.

WebKit은 설치된 browser build와 제공 Playwright 버전 차이가 있고 실행/평가가 완료되지 않아 중단했다. 성공한 WebKit/Safari/iPhone 결과는 없다. 원시 수치: `docs/미디어-재사용-browser-audit.json`. 조사 스크립트/합성 파일은 `/tmp/mori-webp-browser-audit/`에 있으며 제품 소스는 바꾸지 않았다.

## 3. 실제 파일 제공 경로 — 코드 확인

| 항목 | 확인한 현재 동작 |
|---|---|
| 발급 전 접근 검사 | `uploads/repository.py::visible_asset`: 현재 소유자·앨범/페이지·ready·미삭제·현재 연결 참조 검사. source/transform_output은 일반 발급 대상 아님 |
| local GET | `uploads/routes.py::media`: 세션 인증+현재 소유권+서명/만료 확인, `FileResponse(media_type=asset.mime)`, `Cache-Control:no-store` |
| R2 GET | `service.media_access`에서 소유권 확인 후 `R2Signer→sign_get`으로 최대300초 presigned GET. 다운로드 때 앱 세션을 다시 확인하지 않는 bearer URL |
| R2 저장 | `_write`는 검증 파생본의 MIME을 ContentType으로 저장하고 조건부 write로 불변성 유지 |
| 표시 | `SignedPhoto.tsx`의 `<img src=...>`로 표시. 파일 bytes를 HTML로 삽입하거나 실행하는 코드 없음 |
| 제공 헤더 한계 | 사진 local 경로·R2 sign_get에는 명시적 nosniff/Content-Disposition override가 보이지 않음. Caddy도 해당 헤더를 추가하지 않음. 운영 HTTP 응답 자체는 확인하지 않음 |
| 삭제/세션 종료 | R2 기발급 URL은 만료/객체 삭제 전 접근 가능. 계약501행에 명시. ‘항상 소유자 세션 필요’라고 표현하면 부정확 |

따라서 marker 잔존을 바로 XSS/코드 실행으로 판단할 근거는 없다. 사진 파일을 받은 사람은 bytes를 읽을 수 있으므로 실제 개인정보 메타데이터 제거와 URL 보호는 중요하다. nosniff 같은 헤더 보완 검토는 파일 제공 정책의 별도 항목이며, 이것만으로 서버 재인코딩 의무를 도출하지 않는다. 운영 bucket 공개 여부/CORS/실제 HTTP 헤더는 이번에 조회하지 않았으므로 코드·문서상 private 설계와 실운영 검증을 구분한다.

**후속 호환성 발견:** 현재 `visible_asset`는 normalized를 draft/processing/action_required에만 제공한다. normalized를 새 정책의 result로 연결하면 published에서 접근할 수 있도록, run 정책과 실제 result 참조를 확인하는 좁은 예외가 필요하다. 전체 normalized 공개로 바꾸지 않는다. 계획 Task 5에 추가했다.

다음 구현에서는 현행 계약134행을 새 검증/조건부 재사용 규칙으로 개정하고, 서버가 클라이언트 신고를 신뢰하지 않고 실제 파일을 검사하도록 한다. 모든 숨은 데이터 제거·암호학적 썸네일 내용 동일성은 추가하지 않는다. 새로운 운영 실행이나 유료 API 호출은 하지 않았다.

## 실행 환경·제약

- macOS 26.3.1 arm64, Python 3.12.14, Pillow 12.3.0, libwebp 1.6.0.
- Codex 제공 별도 Python runtime 사용. 프로젝트 lock의 Pillow 12.3.0과 일치하지만, Linux wheel/libwebp·운영 이미지의 동일성은 확인하지 못했다.
- Docker 조회는 처음 sandbox socket 접근에 막혀 승인 경로로 재조회했으나 daemon 연결 불가였다. 자동 승인 거절이 아니라 Docker 미실행 상태다. Docker를 시작하거나 QA 컨테이너를 변경하지 않았다.
- 이 runtime에는 pytest/pillow-heif가 없어 표준 unittest로 독립 probe를 실행했다. 새 패키지 설치 없음. 기존 전체 normalizer/HEIC suite는 실행하지 않았다.
- 1GB/no-swap·512MiB Linux RSS 제한 시험, 실제 브라우저 생성 파일, 실제 사진 화질/대규모 성능은 미실행이다. 당시의 과도한 gate 기준으로 진행을 멈췄으며, 그 판정은 위 재판정으로 대체했다. 제품 검사기는 아직 구현하지 않았다.

## 방법과 재현 결과

기존 `backend/tests/media/test_normalization_policy.py::test_ignored_private_payload_removed_by_reencode`의 반례를 출발점으로, 합성 RGB/RGBA 이미지를 손실/무손실 WebP로 만들었다. 실제 개인정보 없이 `SYNTHETIC_PRIVATE_PAYLOAD_location=fixture_only!!` 문자열을 사용했다. 해당 문자열을 넣은 뒤 RIFF/청크 길이와 패딩을 올바르게 다시 계산했다.

독립 probe는 총 29개 케이스를 관측했다. 외부 구조 검사는 RIFF 전체 길이·청크 범위·0 패딩을 확인하며, codec bitstream 검사기라고 표현하지 않는다. 정상 파일과 변경 파일을 RGBA로 전체 디코딩해 픽셀 bytes를 비교했다.

| 주입 위치/종류 | 결과 |
|---|---|
| VP8 끝 내부 (RGB/RGBA 2개) | 외부 구조 검사 통과, 디코딩 성공, 원본과 픽셀 동일, marker 잔존 |
| VP8L 끝 내부 (RGB/RGBA 2개) | 위와 동일 |
| ALPH 끝 내부 (RGBA 1개) | 위와 동일 |
| RIFF 바깥 데이터 (4개) | 엄격한 외부 길이 검사는 거부하지만 디코더는 정상 픽셀 반환 |
| unknown JUNK 청크 (4개) | 외부 길이 검사/디코딩 통과, marker 잔존. 청크 제거로 이 위치만 정리 가능 |
| EXIF/XMP/ICCP marker (3개) | 디코딩 성공. ICC 사례는 실제 정상 색상 프로파일 검증이 아닌 단순 데이터 보존 관측 |
| 중복 이미지 청크 (4개) | 3개는 디코딩 성공, RGBA lossy 1개는 실패. 디코더 성공만으로 유일성 보장 불가 |
| 잘린 파일 (4개) | 외부 구조 검사와 디코딩 실패 |
| animation (1개) | 실제 다중 프레임 확인 후 probe의 단일 프레임 정책에서 거부 |
| clean (4개) | 정상 디코딩 |

추가 unittest는 비정상 padding/헤더·거짓 VP8X 크기·기존 child timeout을 검사한다. 실제 전체 메모리 제한 동작을 검증한 것은 아니다.

내부 payload 반례 5개는 허용 청크 `{VP8X, VP8 , VP8L, ALPH}`만으로 구성되어 있어 청크 allowlist도 통과한다. 같은 청크를 다시 묶어도 marker가 남는다. 픽셀을 새로 인코딩하는 대조 경로에서는 시험 marker가 제거됐다. 이 대조 경로는 Pillow 픽셀 인코딩이며 프로젝트 normalizer 전체를 실행한 결과가 아니다.

설치된 `PIL.WebPImagePlugin.WebPImageFile`을 읽어 `WebPAnimDecoder.get_info/get_chunk/get_next` 사용을 확인했다. 이 경로에서는 payload의 정확한 유효 끝 위치를 반환받지 않는다. [libwebp API 문서](https://developers.google.com/speed/webp/docs/api)는 디코딩·특징 조회를 제공하지만 이 고수준 경로를 잔여 데이터 정리기로 보장하지 않는다. [WebP 컨테이너 명세](https://developers.google.com/speed/webp/docs/riff_container)에 맞춘 외부 구조 검사도 내부 codec 검사를 대신하지 않는다.
