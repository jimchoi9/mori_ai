# 검증·생성 성능 및 회상형 글귀 보완

2026-10-16 사용자 승인에 따라 Orca Run `run_7c6303f3554a`에서 수행했다. 상세 수치는 [측정 데이터](performance-2026-10-16.json), 구현 순서는 [계획](superpowers/plans/2026-10-16-performance-caption.md)을 따른다.

## 변경

- 구간별 JSON 계측: 검증 입력/정규화/저장, 생성 실행/AI 요청/결과 저장, R2 요청/다운로드. 원본 오류 본문·URL·object key·자격증명·글귀·사진 내용은 기록하지 않는다. HTTP 오류 상태와 예외 종류는 남긴다.
- R2 원본을 검증 중 3회, 글귀/이미지 입력 준비 중 각각 3회 내려받던 경로를 1회 authoritative read로 바꿨다. 크기와 SHA-256을 검증한 바이트를 실제 처리에 그대로 사용하며, 재시도는 다시 authoritative read한다. 서로 다른 입력이 필요한 optimize는 입력마다 1회 읽는다.
- 작업마다 전용 임시 파일을 사용한다. 삭제·fence·소유권 확인과 결과 영속화 경계는 유지했다.
- 단일 worker 프로세스에서 검증 1 / 글귀 4 / 이미지 2 / 결과 최적화 1 lane을 실제 실행한다. maintenance·정리 scanner·OAuth 정리는 독립 실행한다. 생성 상한은 DB claim에서 전역·run별로 검사하며, 검증 상한은 프로세스별이다. 전체 큐 길이의 별도 상한은 추가하지 않았다.
- R2 연결 종료 오류의 `response=None` 처리 결함을 수정했다. R2 요청은 standard SDK 재시도를 최초 포함 최대 3회로 제한한다. 조건부 PUT과 불변 객체 확인으로 저장 멱등성을 유지한다. OpenAI SDK 재시도 0, unknown 재호출 금지, 원장 예약 규칙은 유지한다.
- 새 생성은 `openai-memory-v3`: 구체적인 시각적 단서 하나에 기대는 담백한 회상, 자연스러운 ~다 체, 20~45자 목표/최대 80자. 관계·감정·장소·날짜·사연을 지어내지 않는다. 기존 `openai-v1` 및 첫 QA의 `openai-memory-v2` run은 원래 프롬프트를 보존한다. v2의 실제 합성 호출에서 시적인 비유가 나와 v3에서는 비유·의인화와 사진에 없는 행동을 명시적으로 배제했다. 기존 글귀와 이미지 프롬프트는 바꾸지 않는다.

## 같은 입력으로 비교한 결과

Docker VM: ARM64, 8 CPU, 약 8GiB. runtime은 기존과 같은 amd64 실행이다. 이 비교에서 아키텍처·해상도·품질·codec 설정을 바꾸지 않았다. 실제 사진 대신 seed가 고정된 4032×3024 합성 RGB를 JPEG·PNG·HEIF로 인코딩했다. 각 형식/방식 1회 표본이며 네트워크 및 동시 로컬 부하 변동이 있으므로 통계적 성능 보장은 아니다. 두 방식 모두 동일한 최종 R2 재시도 설정을 사용했다.

| 구간 | 기존 경로 | 개선 경로 |
|---|---:|---:|
| JPEG 검증·정규화·저장 | 18.80초 | 23.93초 |
| PNG 검증·정규화·저장 | 31.95초 | 25.23초 |
| HEIF 검증·정규화·저장 | 26.11초 | 17.49초 |

각 형식의 정규화 WebP SHA-256이 전후 일치했다. 순수 정규화는 약 5.2~6.3초였고, R2 저장은 성공 표본에서도 약 8.9~16.4초로 변동했다. 앞선 비교 시도에서는 저장 32.2초와 연결 종료도 관찰했다. JPEG는 개선 경로가 더 느린 표본이므로, 다운로드 감소를 전체 지연의 고정 개선율로 해석하지 않는다. 로직 외에 저장소 통신 지연이 남아 있다. 통신의 ISP·프록시·R2 내부 원인은 이번 증거만으로 구분하지 못했다.

별도 격리 PostgreSQL 비교는 동일한 6장 입력·실제 codec·글귀 1.5초/이미지 3초의 **가짜 provider 지연**을 사용했다. 순차 22.861초 → 병렬 7.991초, provider 호출은 둘 다 9회, 동시 provider 실행 최고치는 1 → 6이었다. 이는 스케줄러의 병렬화 효과이며 실제 OpenAI 지연 수치가 아니다.

공개 API/DTO와 DB migration 변경 없음. 새 구현이며 기존 `moriai` 코드 이식 없음. 프로덕션 배포, 다중 worker 환경의 장시간 부하, 실제 사용자 사진의 새 글귀 만족도, 실제 OpenAI를 사용한 전후 전체 시간 비교는 이번 검증에 포함하지 않는다.

### 2026-10-17 업로드 확인 시간 초과 보완

사용자가 동일한 브라우저 대기 시간 초과 문구를 두 번 보고했다. 해당 문구는 API의 30초 timeout/abort 처리에서 나온다. 웹 성능 logger가 활성화되지 않아 과거 두 요청의 경로·시각은 확정할 수 없다. 별도로 worker 기록에서 15:39:34 KST 시작한 검증의 R2 입력 다운로드가 141.4초 뒤 ReadTimeoutError로 실패하고, 재시도는 55.3초 뒤 성공한 것을 확인했다. AI 호출 실패와는 구분한다.

원인 후보인 upload complete는 HTTP 응답 전에 R2 HEAD와 전체 GET/cache 파일 해시 계산을 기다리고 있었다. R2 경로는 bounded read_bytes 한 번으로 크기·SHA256을 함께 계산하도록 변경했다. 해시 불일치 409, 소유권 검사, 완료 후 삭제 재확인, upload_id 멱등성 계약은 유지한다. 최초 확인의 다운로드 자체는 유지된다. 검증 worker의 별도 authoritative 읽기도 유지한다.

업로드 complete POST에만 브라우저 대기 한도를 180초로 적용하고 전송 확인 중 안내를 표시한다. 일반 API는 30초, 사용자 취소는 즉시 유지한다. 이는 느린 R2 연결의 근본 해결이나 무제한 대기를 뜻하지 않는다. 전체 다운로드가 180초를 넘으면 같은 예약으로 재확인해야 한다. 웹의 안전한 성능 로그를 활성화하고 upload.complete/request_id 및 upload.confirm_input 시간을 추가했다. 사진·URL·해시·사용자 본문은 기록하지 않는다.

실제 사용자 동일 사진 재검증과 네트워크 원인 구분은 남아 있다. 이번 수정 과정에서 실제 AI 호출은 수행하지 않았다.

검증: 수정 전 frontend 30초 제한 회귀 실패 및 backend 별도 HEAD 접근 회귀 실패를 재현했다. 수정 후 frontend typecheck/build 및 관련 테스트 14개, 격리 PostgreSQL의 업로드·R2·삭제 동시성·성능 로그 테스트 54개가 통과했다.

## 사진 축소 품질·개별 Luna 병렬·다중 사용자 실험 — 2026-10-28

사용자가 테스트 실행을 승인하고 **사람·행동·분위기를 단서로 그때를 떠올리는 짧은 한 문장**을 품질 목표로 확정했다. 정밀 OCR은 목표가 아니다. 이번에는 테스트 도구와 문서를 추가했으며 제품의 prompt, snapshot, worker 동시성, 기존 글귀와 배포 이미지는 바꾸지 않았다.

### 결론과 권고

- Luna 분석본은 긴 변 1024px을 유지한다. 단체사진을 포함한 소량 비교에서 사용자 목표에 중요한 장면 단서가 유지됐고, 2048px 대비 비용이 약 60% 낮았다.
- 묶음 요청으로 바꾸기보다 개별 2개 병렬을 다음 구현 후보로 권고한다. 같은 10슬롯의 평균 완료 시간이 24.97초에서 11.11초로 줄었고 평균 비용은 같았다. 4개 병렬은 6.25초지만 실제 제품에 적용한 결과는 아니다.
- 여러 사용자 데이터 처리의 기반은 확인했지만 쾌적한 동시 이용 준비가 끝난 것은 아니다. 현재와 같은 1초 polling에서 10명×20장의 저장·가짜 글귀 완료에 364초가 걸렸다. 사진 저장 검증의 대기를 먼저 줄여야 한다.
- 문체는 별도 개선 항목이다. ‘사진첩을 다시 보니/넘기다’가 반복됐고, 72개 글귀 중 3개가 목표 45자를 넘었다. 기존 문구를 잘라내거나 재생성하지 않았다.

### 실제 Luna: 저장본2048 대 분석본1024

기존 앨범 5장과 사용자가 첨부한 단체사진 1장, 총 6장의 각 입력을 한 번씩 비교했다(12호출). 첨부 JPEG는 5712×4284, 5,001,295bytes다. 연구용 Pillow로 EXIF 방향을 적용하고 2048/Q85 WebP 395,824bytes를 만들었으며, 1024 분석본은 1024×768, 91,304bytes였다. 이는 브라우저 전처리 규격을 근사한 연구 입력으로, 실제 Safari의 인코딩 속도나 출력 동일성을 시험한 것이 아니다. 원본 5MB를 그대로 Luna에 보내지는 않았다. 기존 5장은 서비스에 저장된 2048 WebP를 사용했다.

### 가짜 AI: 다중 사용자 저장 부하

격리 PostgreSQL17, 로컬 임시 저장소, 실제 HTTP 핸들러(ASGI in-process), 실제 미디어 검증 subprocess, 현재의 single-content·single-validation scheduler로 시험했다. 서로 다른 계정으로 테스트 구매를 거쳐 전용 앨범을 생성하고 동시에 각 20장을 파일별 예약→PUT→complete로 보냈다. 계정별로 다른 SHA를 가진 2048×1536 합성 WebP(약 0.32~0.53MB), 원래 해상도 힌트 5712×4284를 사용했다. 썸네일을 별도 전송하지 않는 유효 경로로 서버가 썸네일을 생성한다. 브라우저 일반 경로의 쌍 전송과 전처리 속도는 측정하지 않았다.

첫 진단은 polling을 0.1초로 가속했다. 이후 현재 승인 로컬과 같은 1초로 10명 조건을 별도 시험했다. 가짜 AI에 인위적인 2초 지연은 넣지 않았다. 아래 수치는 실제 Luna가 포함된 전체 체감 시간이나 운영 서버 처리량이 아니다.

- 예약 응답 분실을 가정한 동일 key/body 재전송과 complete 중복에도 추가 페이지·글귀 job이 생기지 않음.

1초 조건의 사용자별 첫 사진 저장은 2.36~21.93초, 전체 20장 저장은 340.59~363.01초였다. complete 이후 ready까지 180초를 넘긴 파일은 99개, 가장 긴 서버 저장 확인 지연은 348.18초다. **99개를 화면 실패 수로 해석하면 안 된다.** 프론트는 두 개의 확인 chain을 사용하며 각 verifyPhoto 함수가 실행된 때부터 180초를 센다. 전체 대기 시간과 실제 UI 오류는 다르고, 이번에는 Safari/JS 확인 chain의 실시간 실행을 시험하지 않았다. 결과 원본의 `max_save_confirmation_seconds` / `save_confirmations_over_180s`는 서버 complete→ready 지연을 뜻하며, 이후 도구에서 `max_server_ready_delay_seconds` / `server_ready_delays_over_180s`로 이름을 명확히 했다.

2GiB 제한을 건 테스트 컨테이너의 cgroup 수치에는 ASGI 서버·worker·driver·미디어 자식·파일 캐시가 포함되고 PostgreSQL과 운영 OS는 제외된다. 연속 case의 임시 파일 캐시도 포함될 수 있으므로 worker RSS나 운영 2GB 합격으로 보고하지 않는다. 네트워크/TLS, 실제 휴대폰 압축·HEIC·화면 잠금·복귀, R2, 실제 AI 포함 전체 경로, 여러 호스트와 장시간 운영 부하도 이번 범위 밖이다.

### 원인과 다음 구현 후보

현재 `_poll`은 일을 처리한 뒤에도 1초 기다리고, validation lane 하나가 사진 검증과 자산 정리를 함께 처리한다. 글귀 요청만 병렬화해도 이 대기는 남는다. 우선 작업이 있는 동안 불필요한 고정 대기를 줄이고 유휴 때만 기다리는 방식, 검증과 정리의 공정성, 사용자·앨범별 대기 정책을 검토한다. 전체 poll 설정을 단순히 0.1초로 배포하면 유휴 DB 조회도 늘어나므로 가속 실험 값을 그대로 적용하지 않는다. 휴대폰 고해상도 decode·압축 lane은 늘리지 않는 방향이다.

추가 DB 검사에서는 8개 worker가 동시에 scan/claim해도 job 중복 없이, 기존 legacy caption 1개가 실행 중일 때 신규 job은 3개까지만 입장했다. 슬롯이 비워진 만큼만 추가 입장했다. 이는 전역 caption4 합산 보호의 검증이며 새 제품의 2/4개 polling lane 배포를 뜻하지 않는다.

## 저장 큐·글귀 2병렬·짧은 문구 반영 — 2026-10-28

사용자가 앞 절의 구현 권고를 승인했다. 공통계약v1.19를 적용하고 기존 snapshot/글귀는 보존했다. 제품 변경은 다음과 같다.

- `worker/scheduler.py`: validation과 album_content만 성공적으로 처리한 작업 뒤에 다음 작업을 바로 확인한다. `True` 반환일 때만 연속 처리하고 `False`/`None` 또는 예외는 기존 polling 간격으로 대기한다. 각 반복은 event loop에 제어를 양보하며 종료 시 owned task를 정리한다. legacy generation·goods·메일의 polling 정책은 그대로다.

### 굿즈에 첨부한5MB사진의 실제 축소 경로

사용자의 질문에 맞춰 제공한5,001,295bytes JPEG를 네트워크 차단 컨테이너에서 실제 `normalize_goods_source`와 `suggestions.thumbnail`으로3회 처리했다. 원본을 Luna에 직접 전송하는 추가 유료 비교는 하지 않았다.

| 단계 | 크기/용량 | 로컬3회 중앙값 |
|---|---|---:|
| 첨부원본 | 5712×4284 / 5,001,295bytes | — |
| 굿즈 서버 정규화 | 2048×1536 / 393,050bytes | 2.702초 |
| Luna 추천 분석본 | 512×384 / **20,568bytes** | **0.079초** |

분석본은 원본 대비 약99.59% 작은 파일이다. 이 측정은 macOS 위 amd64 Docker의 서버 처리 시간이며 Safari 압축 시간·휴대폰 업로드 시간·Luna 응답 시간이 아니다. 굿즈 프론트는 가능한 형식에서 업로드 전에2048/Q85로 축소를 시도하고, 미지원/실패/원본보다커짐이면 원본을 서버로 보낸다. 서버는 그 경우도 정규화한 뒤 추천용512/Q75 분석본을 만든다. 굿즈 이미지 생성 입력과 Luna 추천 분석본은 별개이며512본을 제작/이미지생성 입력으로 대체하지 않았다.

축소는 요청 전송량을 줄이지만 총 AI 응답이 항상 빨라진다고 단정할 수 없다. 앞선 굿즈2048/512 완료2쌍에서는 입력토큰2917동일,총응답속도우위미확인이었고3번째2048요청timeout은unknown으로보존했다.512축소와summary/동일요청cache는 이미 구현되어 있어이번에추가로굿즈추천설정을바꾸지않았다. 로컬측정로그`.local/goods-5mb-sizing.log`,외부통신/과금0.
